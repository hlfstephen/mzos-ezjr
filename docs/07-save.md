## 1. 为什么是"延迟备份"，而不是"游戏里按组合键退出"

EZ-Flash Junior 进游戏后，`$7Fxx` 那组命令寄存器就被 MBC 顶掉了 ——
游戏看到的是普通的卡带内存空间，**内核再也拿不回控制权**，只能断电重启。
官方内核也一样（`$7FE0=$80` 复位进游戏后就不再返回）。

所以存档只能做成三段式，靠**电池供电的 PSRAM** 当中转：

| 时刻 | 谁在跑 | 做了什么 |
|---|---|---|
| 启动游戏前 | 内核 | 把 `<ROM名>.SAV` 读进 PSRAM 存档区，在元数据页盖一个"待备份"章 |
| 游戏里 | 游戏 | 游戏正常写它的"电池 RAM"，物理上落到同一片 PSRAM |
| 下次开机 | 内核 | 看到章还在 → 把 PSRAM 存档区写回 `.SAV` → 清章 |

关键点：**盖章是按"每次启动"而不是"存档有没有变"**。所以没存档也会走一遍
备份流程，代价是多写一遍同样的数据（几十毫秒）。这和官方内核的
`BACKUPSAVE` 行为一致（见上游 `docs/psram-save-map.md`）。

副作用要提前说清楚：**如果玩完直接拔卡不重启，存档就还停在芯片里**，
下次开机才会写进 SD 卡。芯片靠纽扣电池保持，电池没电则存档和 RTC 一起丢 ——
这是硬件层面的限制，软件绕不过去。

## 2. PSRAM 布局（与官方内核同一套）

| 页（8KB/页） | 用途 | 我们怎么用 |
|---|---|---|
| `$00`–`$0F` | 存档 RAM（16 页 = 128KB，MBC 的上限） | 按 `$0149` 决定用前 1/4/8/16 页 |
| `$11` | 元数据 | `$A000`=`$AA` 待备份、`$A001`=块数、`$A00F`=名长、`$A010`+ 名字、**`$A201`=`$88` 电池哨兵** |
| 其余 | 官方文件浏览器记录 | 不碰 |

访问方式（kernel 模式）：`$4000 = 页号` → `$7FC0 = 3` → 读写 `$A000-$BFFF`。
用完 `$4000 = 0`、`$7FC0 = 0`。这套序列照抄上游 `psram_map()` / `psram_unmap()`。

因为字段与官方一致，如果哪天刷回官方内核，它看到我们盖的章也能照常备份。

## 3. `.SAV` 长什么样

- 位置：**根目录的 `SAVER/` 子目录，全卡只此一个**（v0.11.0 起，对齐官方内核
  的目录约定）。ROM 在几层子目录里都一样，得到的是 `根/SAVER/xxx.sav`。
  - v0.10.0 曾按 ROM 所在目录各建一个 `SAVER`，理由是避免 `GB/口袋妖怪.gbc`
    与 `GBC/口袋妖怪.gbc` 互相覆盖。真机反馈是：根目录已经有了一个，子目录里
    又冒出第二个，反而乱。用户要的就是官方那种「一个 `SAVER` 收齐」。
  - 代价是同名不同目录的游戏确实会共用一个存档 —— 这是官方行为，接受。
  - 实现上 `saver_find()` / `saver_dir()` 临时把 `fat_cwd` 切到根目录再查/建，
    出口还原；建不出来（卡满 / 目录项写不进）也退回根目录写，不会在子目录里
    留一份散落的 `.sav`。
  - `META_DIR` 仍然记录 ROM 所在目录，但用途已经改成 START 菜单「运行上次游戏」
    的定位（见 [docs/09](09-ui.md#start-菜单)），跟存档落盘无关。
- 名字：**跟 ROM 文件逐字同名，只换扩展名**。这是硬要求 —— 卡上的加载器按
  文件名配对，差一个字就「提示备份成功，但游戏里找不到存档」。
  - 8.3 短名：`POKEMON.GBC` → `POKEMON.sav`；**后缀小写**靠目录项 `+$0C` 的
    bit4（NT 的「扩展名小写」标志），短名本身仍按 FAT 规范存大写 `SAV`。
  - VFAT 长名：ROM 的中文长名换扩展名，逐字照抄。`K 口袋妖怪 水晶 金手指v3+
    全道具251+NPC加强版2.0.gbc` → 同名 `.sav`（36 个字符 = 3 条 LFN 项）。
  - v0.11.0 及以前这里有两个坑，合成一个「备份成功但找不到文件」的真机问题：
    ① `fat_open_sav()` 里 `if (nent > 3) nent = 0` —— 名字长到要 4 条 LFN 项
    就**整条长名都不写**，卡上剩一个只有短名的文件；② `sav_lfn()` 按**第一个**
    点当扩展名分隔，`加强版2.0.gbc` 被切成 `加强版2` + `.sav`，`0.gbc` 丢了。
    v0.12.0 改成：取**最后一个**点、主体不截断、LFN 段数上限放到 9。
  - 长名从哪来：菜单/元数据页那份长名被截到 27 个字符（屏幕一行只画 18 列），
    不够拼存档名。所以备份前用 `fat_full_lfn()`（`src/fatn.c`）回 ROM 所在
    目录、按 8.3 短名把它**完整**的长名重新读出来，再写 `.sav`。这个函数编在
    `_CODE`（BANK1 已满），出口还原 `fat_cwd`。
  - **已知限制（v0.12.2 未修）**：`fat_full_lfn()` 的目录窗口是
    `dir_chain(fat_cwd, chain, 16)` —— **只扫前 16 个扇区 = 256 条目录项**。
    目录项排在第 257 条之后的 ROM 查不到长名，备份屏就退回 8.3 短名。
    自检屏的 `LFN=0`（配合 `REC=OK`）就是这一条的现场证据；
    修法是把 `dir_chain` 加一个「从第 k 个扇区起」的参数、外层分批扫，见
    `CHANGELOG.md` v0.12.2 的「已知限制」。
- 大小：由 ROM 头 `$0149` 决定，8KB / 32KB / 64KB / 128KB。
- 已存在且大小相同 → **原地覆写原簇链**（不重新分配，避免反复存档把卡写碎）；
  大小不同 → 回收旧链、重新分配。
- **升级兼容**：读存档时先找 `SAVER/`，找不到再回落到 ROM 同目录
  （v0.9.0 及以前写在那儿）。老 `.SAV` 留在原地不搬迁，下次备份时在
  `SAVER` 里生成小写的新文件，老文件可以自己删。

## 4. 这一版动了代码布局（真机最大的未知数）

加完存档后代码涨到约 20.6 KB，`_CODE` 冲出 `$4000` 会压到 ROM 后半段上。
处理办法：把「不常执行但占地方」的模块编到 `BANK1` 段。v0.12.6 的实际布局：

```
_CODE   $0400-$3B0A   主流程（列表、设置时间、启动）+ fatx.c + fatn.c + video.c
_BANK1  $4000-$7E93   save.c + fat.c + fatw.c + fpga.c + fatx.c
```

`--diag` 版多编 1.1 KB 的自检屏，`_CODE` 收到 `$3FA0`（**只剩 96 字节余量**）、
`BANK1` 到 `$7FAF`（余 81 字节）。余量这么紧是有历史的：`fatn.c` 里那个近
900 字节的 `fat_full_lfn()` 只能放 `_CODE`，为此又删掉了没人调用的
`fat_next_cluster()`（顺带去掉它那个 512 字节的栈上缓冲）、把 `fpga.c` 挪进
`BANK1`，才重新塞回 32 KB 以内。

> v0.12.2 加自检屏的 `REC/DIR/LFN` 三行时，`_CODE` 第一次是冲出去的
> （$4094，超 148 字节）。解法不是再挤别的模块，而是把「取值 + 画这三行」
> 整体放进 `save.c` 的 `diag_last_record()` —— `save.c` 在 `BANK1`，
> 那儿还有五百多字节，而这个函数读的又正是 `save.c` 的私有状态。
>
> v0.12.3 再加 `RAW` / `B` / `WR` 三行时 `BANK1` 一路顶到 `$7F61`：原本写了个
> 4 字节十六进制打印器（约 75 字节），为了省空间改成用现成的 `print_dec2()`
> 印两个十进制字节（`80,79` / `255,255`），前者是 ASCII 的 `PO`，后者是擦除态，
> 判读同样直接。
>
> v0.12.6 要给 `fatw.c` 补「长名跨扇区」（约 60 字节），`BANK1` 只剩 30 字节，
> 于是把 `RAW` / `K` 两个探针整个撤掉 —— 它们的使命（分清"没写过"和"写了但
> 校验错"）在 v0.12.4 换到 `$A300` 时就完成了，留着只是占地方。
> **现在余量 81 字节，再加东西前先想清楚放哪一段。**

**32KB 的 GB 卡带本来就分两个 16KB bank**，`$4000-$7FFF` 就是文件的后半段，
所以跨段 `call` 只是地址不同，header 仍写 ROM ONLY，不需要切 bank。

⚠️ 这是一个**只能在真机上最终确认**的假设。间接证据有一条：模拟器自检版
（`EZJR_TEST=1`）的 `diag.c` 也在 `BANK1` 段，PyBoy 里 START 进自检屏、
14 行读数全部正常 —— 说明跨段 `call` 生成的机器码本身没问题，剩下的变量只有
"真机的 32KB 卡带映射是不是也把 $4000-$7FFF 当 ROM bank 1"。如果开机就白屏 /
卡在引导 / 连列表都出不来，很可能就是这里，请先用 `restore/ezgb.dat` 回滚。

## 8. v0.3.0 事故复盘：`.SAV` 里躺着根目录扇区

### 现象

真机 S4 显示 `SAVING SAVE` → `SAVE OK`，卡上出现 `POKEMON.SAV`，32768 字节。
但再进游戏读档，存档没了。用户把那个 `.SAV` 发过来，解出来是这样：

```
000000  45 5a 47 42 20 20 20 20 44 41 54   EZGB    DAT     ← 目录项
000020  e5 a0 52 3a 5f 48 72 32 00 2e 00   ...LFN 项...
000080  ...31 20 53 41 56 20              "1 SAV"          ← 我们自己那个文件
```

64 个扇区里只有 3 种内容，全是**刚才读过的根目录扇区**。

### 根因：`$7FC0` 与 `$7F30` 是互斥的两种窗口

RTL（`stage0/rtl/sd_mem_path.v`、`gb_data_out.v`）：

```verilog
assign win_sel = win_kernel & !win_mode[0] & !win_mode[2];   // win_mode = $7FC0 的 bit3:0
assign buf_en  = win_sel & win_en;                           // win_en = $7F30 bit0
wire  status   = !cmd_b4_flag ? 8'he1 : win_en1 ? 8'h01 : buf_q;
```

- **SD 扇区窗口**要求 `$7FC0` 的 **bit0 = 0 且 bit2 = 0**（也就是 `$7FC0 = 0`）；
- **PSRAM 页模式**正好是 `$7FC0 = 3`（bit0 = 1）；
- PSRAM 那个窗口另有判据：`win_not3 = !win_mode[0] | ...`，`$7FC0 = 3` 时才把
  `$A000-$BFFF` 接到 PSRAM。

两者**不能同时有效**。而 `save.c` 的循环是：

```c
psram_map(page);                       /* $7FC0 = 3 */
memcpy(game_work, WINDOW + ..., 512);  /* 读 PSRAM，对的 */
err = fat_write_sec(&f, game_work);    /* 少了 psram_unmap() ！ */
```

于是 `sd_write()` 里那句 `memcpy(WINDOW, src, 512)` 仍然落在 **PSRAM 页**上，
SD 控制器一个字节都没收到 —— 它照旧把自己缓冲区里的旧内容（上一次 `sd_read`
读到的根目录扇区）写出去。屏幕上的 `SAVE OK` 是"命令发出去了"的意思，
不是"数据对了"。

同一个疏漏在 `save_load()` 里更狠：`i ≥ 1` 之后的 `fat_read_sec()` 读到的是
PSRAM 而不是 SD，于是**把半成品又写回 PSRAM**，进游戏时存档就"没了"。

上游 `stage1/src/backup.c` 的循环是：

```c
psram_map(off >> 13);
memcpy(buf, PSRAM + (off & 0x1FFF), 512);
psram_unmap();                 // ← 就是这一句
fat_write(off >> 9, buf);
```

### 修正（三处）

1. **`fpga.c`**：`sd_read()` / `sd_write()` 入口先 `fpga_set($7FC0, 0)`。
   这层保险的意思是"只要走 SD 通路，窗口一定是 SD 的"—— 任何调用方忘了
   unmap 也不会把数据写进 PSRAM。代价是调用者的 `psram_map()` 失效，
   所以要用 PSRAM 的代码必须在**每次** SD 操作后重新 map。
2. **`save.c`**：每块 512 字节都 `psram_map → memcpy → psram_unmap → SD 操作`，
   与上游一致，把意图写在代码里而不是靠 fpga.c 兜底。
3. **`save_boot()` 加回读校验**：写完把 `.SAV` 读回来逐扇区比对，不一致就显示
   `SAVE FAILED / READBACK MISMATCH`（`ERR=9`）。v0.3.0 正是"存坏了却报 SAVE OK"，
   这一条让同样的错误下次能当场看见。

### 顺带修掉的两个隐患

- **卡上没有 `.SAV` 时不再清空 PSRAM**。原来一律清成 `$FF`，等于"没存档就把
  芯片里的存档抹了"。现在只有确认 PSRAM 里是**别的游戏**的数据时才清。
- **元数据页记"上次启动的游戏"（`$1D0` / `$1E8`，本内核自用）**，用来做上面
  那个判断。为什么不放 `$020`：官方内核的 `$010` 起是**最多 250 字节的完整路径**
  （`/SAVER/xxx.SAV`），`$020` 落在它中间，读出来是 ASCII 垃圾，会被误判成
  "别的游戏"从而清掉真存档。

  格式（v0.12.1 起，18 字节，写两份）：

  | 偏移 | 内容 |
  |---|---|
  | `+0..12` | 完整 8.3 名 + NUL（`"POKEMON.GBC"`）|
  | `+13..16` | 所在目录的首簇（0 = 根目录）|
  | `+17` | 校验 = `$5A ^ 前 17 字节` |

  v0.11.0 那套散字段（`$130` 中文长名 / `$170` 长度 / `$171` 目录 / `$180`
  完整名 / `$1F0` 短名）在真机上读回来是空的 —— 散字段没有校验能自证
  「这是本内核写的」，擦除态 `$FF` 和真值分不开，被覆盖一个字节就整组作废。
  现在校验不符就当「无上次游戏」，两份中坏一份还有另一份。
  **长名不再存**：开机按 8.3 名回目录现查（`fat_full_lfn()`）。

  v0.12.3 在这一段上补了两个洞（真机反馈 `REC=--`、备份屏还是短名）：

  | 洞 | 现象 | 修法 |
  |---|---|---|
  | **校验用"写完读回"算** | 写后立刻读若有半拍延迟，落盘的是「名字对、校验按旧值算」的记录 → 每次开机都判无效，和"从来没写过"一个样 | `rec_put()` 的异或改用**入参**（`name[]` / `dir`）累加，不依赖窗口回读 |
  | **记录写在 `if (banks)` 里** | 卡带头 `$149 = 0`（没有存档 RAM）的 ROM 永远记不上：启动、关机、再开机，START 菜单还是「无上次游戏」 | 把 `save_arm()` 提到 `save_prepare()` 的 `if (banks)` **外面**；`save_arm()` 内部只有盖章那几行留在 `if (banks)` 里 —— 记录与"能不能备份"无关 |

  自检屏为此加了 `B` / `V` 两个读数，判读见 `docs/05-hardware-test.md` 第 4 节
  （v0.12.6 撤掉 `RAW` / `K`，只留 `B` / `V` / `REC` / `DIR` / `LFN`）。

  v0.12.6 补的是**写 .sav 那一路**的三个洞（真机反馈「备份显示完成、卡上
  找不到那个中文名 .sav」）：

  | 洞 | 现象 | 修法 |
  |---|---|---|
  | **写盘名字用 `boot_name`** | 那是官方字段 `$00F`/`$010` 的 8 字符基本名，可能是上一个游戏、甚至官方内核留下的 `/SAVER/...` 路径 —— 名字里带 `/` 的话 Windows 直接当非法项**不显示**，而 `save_verify` 用同一个名字去读，照样通过 | 改用 `boot_full`（`$A300` 记录里的完整 8.3 名），和屏幕显示**同源**；记录无效才退回 `boot_name` |
  | **建不出 SAVER 就写根目录** | `fat_cwd = sv ? sv : 0`。文件落进根目录，而 `fat_open_read()` 有"SAVER 找不到就回根目录找"的兜底 → 校验通过、屏幕报「完成」，玩家在 SAVER 里永远找不到 | `!sv` 直接报 `FAT_ERR_ADD_DIR`（屏幕显示「目录已满」），绝不静默换地方 |
  | **长名写不下就静默降级** | `dir_seek()` 只统计**同一扇区内**的连续空槽。SAVER 里 12 个存档占 14 项 = 448 字节，第一扇区只剩 2 槽，而 36 字符的中文名要 3 条 LFN + 1 条短名项 = 4 槽 → 跳过 LFN 只写短名，函数仍返回成功 | 槽不够时把**本扇区尾部**的 `$00`（目录结束标记）全改成 `$E5`（合法空槽，遍历会跳过继续走），重扫一次落到下一扇区开头 —— 那里有 16 槽。只对尾部这么干；夹在中间的空洞改不了，直接报「目录已满」 |

  > 第二、三个洞是**同一类**：失败时**静默换一条路**，而那条路的结果玩家
  > 看不见，屏幕却照样报成功。现在三条路都堵死——要么写对，要么明说。

  v0.13.0 把这一层按 FatFs 的写法重做了（**没有链接 FatFs**，只是照 `ff.c`
  的 `dir_alloc` / `dir_next` / `dir_register` 抄算法 —— 官方内核 160KB / 10 bank
  才装得下整套 FatFs，32KB 装不下）。

  核心只有一句：**`$E5` 和 `$00` 同等看待，都是「能用的空槽」**。

  ```c
  if (dir[0] == 0xE5 || dir[0] == 0x00) {   /* 空槽 */
      if (++run == nent) break;             /* 连续够了就用 */
  } else run = 0;
  ```

  `$00` 不需要「腾位」：写满之后后面本来还有 `$00`，终止符自己就往后走了。
  要更多槽就扩一簇（`create_chain` + `dir_clear`），新簇清零后就是一整片空槽。

  | 函数 | 职责 | FatFs 对应 |
  |---|---|---|
  | `dir_seek()` | 只查找同名项 | `dir_find` |
  | `dir_alloc()` | 找 n 个连续空槽，**允许跨扇区** | `dir_alloc` |
  | `dir_put()` | 按扇区拆开写 LFN + 短名 + 1 条 `$00` 终止符 | `dir_register` |
  | `dir_append()` | 链尾接一簇并清零 | `create_chain` + `dir_clear` |

  早期版本那三条「洞」的最终解释：

  | 洞 | 现在怎么没的 |
  |---|---|
  | 空槽只数一个扇区 | `dir_alloc` 从目录头顺序数，跨扇区、跨簇都算连续 |
  | `$E5` 腾位把目录写死 | **腾位这个动作整个删掉了**。不再改写任何已有字节，`$00` 自然后移 |
  | FAT16 链尾判据用错 | `dir_nth()` 按 FAT 类型分开判（FAT16 `$FFF8`），再加 `c > cluster_count + 1` 栏杆 |

  **目录满不再报错**：`dir_alloc` 凑不齐就 `dir_append()` 扩一簇再来，真的
  没有空簇才报 `FAT_ERR_ADD_DIR`。玩家不用再手动删存档。

### 为什么主机测试没抓到

原来的 `save_host_test.py` 把 `sd_read` / `sd_write` 换成了桩，
`$A000` 窗口根本不存在 —— 谁写进去都"对"。新增
**`tools/window_host_test.py`**：把窗口择路建了个模型，

```c
uint8_t *win_ptr(void) {                 /* 照 RTL 抄 */
    if ($7FC0 == 3)                 return psram + ($4000 << 13);
    if (!($7FC0 & 5) && ($7F30 & 1)) return ($7F30 & 2) ? alt : sdbuf;
    return dummy;
}
```

然后跑**真的** `fpga.c / fat.c / fatw.c / save.c`，覆盖：首次启动不清档、
落盘逐字节等于 PSRAM、再启动装回、换游戏清成 `$FF`、官方元数据页不误判。
把修复回退掉跑一遍，这个测试会失败 —— 它能复现真机上的那个 bug。

## 9. 电池哨兵：没电就别备份（v0.3.2）

### 为什么必须有这一条

存档靠**纽扣电池**供电的 PSRAM 活着。电池耗尽后，PSRAM 里的字节会慢慢漂向
`$FF`（也有漂向 `$00` 或随机值的）。此时最坏的情况不是"存档没了"，而是：

> `$AA` 待备份章**还在**，存档数据的每一个字节已经不是原来那个了。

内核照章办事，把这堆随机字节写进 `.SAV`，**卡上那份好的存档就被换成垃圾了**。
v0.3.0 的事故其实是同一个错误家族：写出去的东西不对，屏幕还报 `SAVE OK`。

官方固件用一字节哨兵挡住这件事，我们照抄。

### 机制：`$11:$A201` 的 `$88`

| | 官方内核 | 我们 |
|---|---|---|
| 位置 | 元数据页 `$11`，偏移 `$A201` | 同 |
| 值 | `$88` = 卡带初始化过 | 同 |
| 判定 | `BatteryCheck`（`00:1835`）读它，**不是 `$88` 就是 BATTERY DRY** | `save_boot()` 开头 |
| 提示后 | 重新盖章 `$88` | 同 |
| 有没有存档 | 都重新盖 | 同 |

流程：

```
开机 → 读 $A201
        ├─ = $88（电池还在）→ 盖章 $88 → 有 $AA 章？→ 备份 → SAVE OK
        └─ ≠ $88（BATTERY DRY）→ 盖章 $88
                                 ├─ 有 $AA 章 → 屏上 BATTERY DRY / NOT BACKED UP
                                 │              清掉章，**一个扇区都不写**
                                 └─ 没章 → 静默（PSRAM 已经空成 $FF，没什么可提醒）
```

盖章是"从这一刻起，PSRAM 有电、内容是真的"的意思。所以 DRY 之后仍然要盖 ——
不然下次开机还是 DRY，永远恢复不了。

**为什么不用 PCF8563 的 VL 位**：官方内核明确不看它（`docs/psram-save-map.md`：
"It never reads the RTC chip's voltage-low flag"）。VL 只在电压跌破阈值那一刻
置位并保持，电池耗尽后回光一次、或者用户设过一次时间，它可能就清成 0 了，
而 PSRAM 里的数据早废了。哨兵字节直接反映"**这片 PSRAM 保住电了吗**"，
比电压标志更贴近要判断的事情。

### 副作用：第一次开机一定会判 DRY

新卡 / 刚从官方固件或 v0.3.1 升级上来的卡，`$A201` 里没有 `$88`，所以第一次
开机就是 BATTERY DRY —— **官方固件也是这个行为**。这一轮不会备份（哪怕芯片里
真有存档），盖完章之后一切正常。

这条误判方向是安全的：宁可这一轮不备份，也不拿垃圾去覆盖卡上的好文件。
真遇上"升级前芯片里有没来得及导出的存档"，只能接受丢掉那一次。

### 顺手补的一处

`save_prepare()` 里「上次启动的是哪个游戏」这条记录（`$1D0`）同样靠电池保活，
DRY 之下一律不可信。现在 DRY 时直接按「别的游戏」处理：

- 卡上**有** `.SAV` → 正常装进 PSRAM（本来就会覆盖，无所谓）；
- 卡上**没有** `.SAV` → 清成 `$FF`，等于新卡带该有的样子。

留着衰减后的字节，游戏会提示存档损坏；《水晶》甚至会卡在读档界面不动。

### 验证

`tools/window_host_test.py` 的用例 6（`op 'd'`）复现了这个场景：哨兵是 `$FF`、
`$AA` 章还在、存档区是 `$FF/$00` 交替的衰减数据。断言：

1. 屏幕是 `BATTERY DRY` / `NOT BACKED UP`；
2. **写盘扇区数 = 0**；
3. 卡上原有的 `.SAV` 逐字节不变；
4. 哨兵已重新盖成 `$88`；
5. 接着启动另一个游戏时 PSRAM 清成 `$FF`；
6. 恢复供电后的下一次开机照常备份成功。

把 `save_boot()` 里的电池门去掉再跑，前三条会失败 —— 它就是能复现"没电时把
卡上的好存档写成垃圾"的那个测试。

## 10. 备份一次就够：内容指纹（v0.3.3）

### 问题

v0.3.2 只要看到 `$AA` 章就备份。章是「启动游戏时盖的」，意思是**这个游戏被启动过**，
不是「存档变了」。于是：

- 进游戏看一眼、没存档 → 开机还是备份一遍（白写 64 个扇区，还闪一次 `SAVING SAVE`）；
- 在电脑上把备份好的 `.SAV` 拷回卡上想还原 → 一开机又被打回芯片里的内容，
  **用户想覆盖存档这件事做不到**。

### 做法：比内容，不比"启动过"

备份成功时，把存档区（`banks × 8KB`）算一个 24 位指纹，连同有效标记 `$5A`
存在元数据页 `$11` 的 `$A110-$A113`（本内核自用，官方内核不碰这段）。

开机时：

```
读 $A113 == $5A？ ── 否 ──→ 没有指纹（第一次升级上来）→ 备份一次，建立指纹
                  └ 是 ──→ 算当前指纹，与记录的比
                             ├ 相同 ──→ 直接返回，卡一个字节都不动，屏也不闪
                             └ 不同 ──→ 备份，成功后更新指纹
```

对应到实际场景：

| 用户做了什么 | 芯片内容 | 结果 |
|---|---|---|
| 游戏里存了档 | 变了 | 备份 ✔ 这正是要的 |
| 进了游戏但没存档就关机 | 没变 | 跳过，不白写 |
| 电脑上拷了 `.SAV` 回卡、没进游戏 | 没变 | **跳过，用户那份保住** ✔ |
| 拷了新存档又进游戏玩了 | 变了 | 备份（写回的就是他玩出来的那份，无害） |
| 第一次升级到这一版 | —— | 备份一次，建立指纹 |

指纹只在**备份成功后**更新。失败（卡满、簇链断、回读不一致）时保留旧值，
这样下次真的存档了、内容一变还是会被认出来。

### 为什么是 24 位而不是 CRC16/CRC32

存档区最大 128KB，算一次要走 256 次 `sd_read`/PSRAM 读。24 位是"碰撞概率
1/1600 万"和"代码只有二十来行、跑起来不到一秒"的折中。就算真撞上一次，
后果是**少备份一次**——`$AA` 章已经清了，下次进游戏存档后内容一变还是会被
发现，不会永久丢档。要的是"别白写卡"，不是密码学强度。

### 验证

`tools/window_host_test.py` 新增两个用例：

- **用例 2b**：备份一次 → 芯片内容不变 → 再开机 → 断言**写盘扇区数 = 0**、
  屏幕上什么都没显示、卡上 `.SAV` 逐字节不变。
- **用例 7**：备份一次 → 模拟"用户在电脑上换了卡上的 `.SAV`"（把首字节翻成
  `$XX`）→ 开机 → 断言一个扇区都没写、用户换进去的那个字节还在。

把 `if (cur == prev) return;` 去掉再跑，这两条立刻失败
（`FAIL 写了 64 个扇区，把用户换的文件盖掉了`）。全量回归 150 项 + 模拟器 50 项全绿。

### 与官方内核的关系

官方 `BACKUPSAVE` 没有指纹，它靠 `$AA` 章 + 用户手动在菜单里选「备份存档」。
我们的指纹是本内核的增强，写在 `$A110` 这段官方不用的位置，**不影响和官方
固件的互操作**：刷回官方固件，它看 `$A000` 的章；刷回我们，指纹还在就继续用。

## 11. 自动 / 手动备份，以及电池没电时的行为（v0.5.0，v0.6.1 调整默认值）

### 两种模式

设置页第二个条目切换，状态记在元数据页 `$11:$A120`/`$A121`：

| 模式 | 开机时的行为 |
|---|---|
| **自动** | 有东西要写就直接写，屏上 `BACKING UP...`，完成后同屏下一行 `FINISHED` |
| **手动** | 先问一句「备份存档 / `A=备份` / `B=跳过`」（中文按钮），玩家按 A 才写 |

> v0.7.0 起备份不再是 `SAVING SAVE` → `SAVE OK` 两屏：进度屏画好后**不清屏**，
> 结果只在下一行局部补（`FINISHED` / `SAVE FAILED`）。确认屏也换成中文按钮
> （`A=备份` / `B=跳过`），并显示中文全名而不是 8.3 乱码。详见 `docs/09-ui.md`。

「有东西要写」仍然由前面两套判据决定：`$AA` 章在 + 内容指纹对不上。所以
**进游戏看一眼没存档，两种模式下都不会问、也不会写**。

按 B 跳过时**不更新指纹**，下次开机还会再问 —— 这是刻意的：用户拒绝的是一次
写卡动作，不是"这份存档永远不要了"。

### 默认值是手动，而且是两个字节

```c
#define META_AUTO 0x120        /* $120 和 $121 都要是 $5A 才算自动 */
#define AUTO_ON   0x5A
#define AUTO_OFF  0x5B
```

v0.5.0 的判定是反过来的（只有 `$5B` 算手动，其余当自动），后果是：**电池没电 →
PSRAM 里的 `$120` 衰减成随机值 → 落回"自动"**，下次开机不问就写卡。这跟"手动"
的初衷正好相反，v0.6.1 改成"只有明确写了 `$5A/$5A` 才算自动"。

为什么用两个字节：单字节时随机值恰好命中 `$5A` 的概率是 1/256，两个字节降到
1/65536。误判成"自动"就会擅自写卡，值得多花一个字节。

### 电池没电时不问

`save_boot()` 的顺序保证了这一点：

```
读 $A201
 ├─ ≠ $88（DRY）→ 重新盖章 → 有 $AA 章？→ 闪 BATTERY DRY / NOT BACKED UP
 │                                        → return ★ 到不了确认屏
 └─ = $88 → 有东西要写？→ 手动模式才问
```

DRY 时芯片里是随机字节，问"要不要备份"等于问"要不要把卡上的好存档换成垃圾"。
所以提示屏只**通知**，不用按任何键，1.5 秒后自己消失。

代码里那个 `if (!auto_bk && !batt_dry)` 的第二个条件是冗余的（DRY 分支已经
return），留着是为了让以后改代码的人一眼看见"确认屏不能出现在 DRY 之后"。

### 一个真实的限制

「自动」这个选择本身存在 PSRAM，**电池没电就丢**，于是回到手动。要真正持久化
得把开关另存到 SD 卡（比如 `EZJR.CFG`），没做 —— 判断是不值得为此多一条写卡
路径和一种新的故障模式。真机测试项 T7c 就是在验这件事（切自动 → 拔电 → 应该
回到手动）。
