# 08 · RTC 基准：让 MBC3 游戏读到真实的墙钟

> 状态：**代码完成（v0.3.3），主机侧验证全绿，真机未验证**
> 依据：`ezjr-104c-fw5-rtc-fix/docs/02-solution.md`（1.04c 内核反汇编 + 补丁实测）
> 和上游 `lukesau/ezgb` 的 `stage0/rtl/mbc3_clock.v`。

---

## 1. 症状

《宝可梦 水晶》是 MBC3+TIMER 卡带（header `$147 = $10`）。进游戏后：

- 游戏内时间从某个固定点开始（常见是 2000-01-01 00:00），或者干脆从"现在"开始按秒走；
- 关机一晚再开，游戏里只过了几十秒；
- 白天/夜晚的差异、每日事件（树果、彩票）都不会正常推进。

主机侧的内核时钟（`rtc.c` 读 PCF8563）是准的 —— 菜单里显示的时间对不对？对。
错的只有**游戏看到的那个时钟**。

## 2. 为什么：FW5 给游戏的是「基准 + 已过时间」

FW5 固件里，MBC3 游戏的时钟不是直接转发 PCF8563，而是两段相加：

```
游戏读到的时钟 = base（上电时内核写的一次性基准） + elapsed（PicoBlaze 数出来的增量）
```

`elapsed` 由 PicoBlaze 盯着 PCF8563 的秒跳变推进（`re/stage0/picoblaze/fw5-0918/bank1.psm`
的 `game_clock`，`$03C` 起）。**`base` 只在上电时由内核写一次，默认是 0。**

官方 1.04c 内核**从来不写这个 base**。于是 `base = 0`，游戏读到的就是"从开机起过了多久"：

| | 官方 1.04c | 本内核 v0.3.3 |
|---|---|---|
| base | 0（从不写） | 上电时的真实 PCF8563 时间 |
| 游戏看到的时分秒 | 00:00:00 + 开机后的秒数 | 真实时间 |
| 关机一晚再开 | 归零重来 | 接上真实时间 |

这也解释了为什么"设过时间、菜单里也对，进游戏还是不对" —— 菜单读的是 PCF8563，
游戏读的是 base+elapsed，两条路。

> ⚠️ 一个常见误解：以为要顺手置 `$7F37` 的 bit7 让 PicoBlaze 跑起来。
> **不要。** 1.04c 的 `bank1 $5901-$5921` 已经按 cart type `$0F/$10` 处置，
> `bank0 $19e7` 的 `LaunchSetup` 会合成进 `$7F37`。在别处再写一次只会覆盖
> MBC 类型。我们写 `$7F37` 是在**替代** `LaunchSetup`（本内核就是启动器本身），
> 写的是完整值（`mbc | rtc_flag`），顺序和原生一致。

## 3. 写哪里：页 6 的 `$A018-$A01C`

`stage0/rtl/mbc3_clock.v` 的解码：

```verilog
wire k_wr = rtc_set_wr & a4;       // a4 = 地址第 4 位
```

- `$A008`（a4=0）→ PCF8563 的实时读数（和设置时间界面用的是同一个地址）；
- `$A018`（a4=1）→ **base 寄存器**（S / M / H / DL / DH）。

⚠️ `$A010-$A014` 是 `$A018` 的**别名**（`k_sel` 不看 a3），而**别的页**上
`$A010` 是存档路径缓冲区。所以必须先 `$7FC0 = 6` 再写，写完立刻切回去。

| 地址 | 内容 | 位宽 |
|---|---|---|
| `$A018` | 秒 | 6 位（0-59） |
| `$A019` | 分 | 6 位（0-59） |
| `$A01A` | 时 | 5 位（0-23） |
| `$A01B` | 天 低 8 位 | 8 位 |
| `$A01C` | 天 bit8 \| halt \| carry | 只写 bit0，bit6/bit7 清 0 |

## 4. ⚠️ 天数只有 9 位：日期不可能等于真实日期

MBC3 的日计数器是 **9 位（0-511）**。这是 1996 年的硬件规格，不是我们的 bug。

从 2000-01-01 到 2026-11-11 是 **9811 天**，写进去只能保留低 9 位 = **83**。
游戏会认为"已经是第 83 天"，也就是 **2000-03-24**。

| | 真值 | 游戏看到 |
|---|---|---|
| 时:分:秒 | 14:30:05 | **14:30:05 ✔** |
| 第几天 | 9811 | 83（9811 mod 512） |
| 游戏内日期 | 2026-11-11 | 2000-03-24 |

**这一版修的是时分秒和"天数在推进"，不是"游戏内日期等于今天"。** 后者做不到 ——
除非游戏自己用存档里的字段记日期（《水晶》确实会存，但它以卡带时钟为准）。

为什么不置 carry（`$A01C` bit7）：carry 表示"天数溢出过"，游戏看到它通常会把
时间**重置为 2000-01-01**，比 83 天更糟。所以清 0，让天数至少是单调推进的。

## 5. 什么时候写、写完回到哪页

```c
if (timer)                 /* header $147 == $0F 或 $10 */
    rtc_base_write();      /* 内部：fpga_page(6) → 写 5 字节 → fpga_page(2) */
```

调用点在 `game_launch()` 里、`$7F37`（MBC 类型）之前。此时加载命令还没搬进
`$A000`，不存在踩踏。

**结束页必须是 2**，不能是 0。`tbl_win = win_sel & win_mode[1] & load_win`，
页 0 的 `win_mode[1] = 0`，会让后面的加载命令窗口整个失效 —— 这是
`ezjr-104c-fw5-rtc-fix` 里查出并修正过的一个真 bug，我们照正确的做。

## 6. VL 置位时什么都不写

`$A008` 的 bit7 是 PCF8563 的 VL（Voltage Low，掉电后时钟完整性丢失）。VL 置位
说明 RTC 芯片自己都承认时间不可信，此时写进去的只会是 2000-01-01 这种垃圾。
所以：

```c
if (RTCWIN[0x08] & 0x80) { fpga_page(2); return; }   /* 一个字节都不写 */
```

让游戏继续从 0 起算，比让它以为"现在是 2000 年 1 月 1 日"更不容易出怪事。

## 7. 验证

### 主机侧（`tools/rtc_host_test.py`）

新增 4 条断言，期望值全部由 **Python 的 `datetime` 日历**生成，不手抄：

| 断言 | 覆盖什么 |
|---|---|
| 20 个时刻 → S/M/H + DL/DH 逐字节正确 | 闰年（2000/2004/2008/2020/2024）、平年 2 月、世纪边界 2099 |
| 结束页是 2（`6 → 2`） | §5 那个真 bug |
| VL 置位时 base 区一个字节都不写 | §6 |
| VL 置位时仍切回页 2 | 早退路径不能漏掉切页 |

两个变异测试确认这些断言真的有效：

- 把 `rtc_days_from_2000()` 里的 `+ (yy+3)/4`（闰年补偿）删掉 → **16/20 个时刻不符**；
- 把结尾的 `fpga_page(2)` 改成 `fpga_page(0)` → **"切页 6 再回 2" 失败**。

### 真机（M1）

同 `docs/05-hardware-test.md` 的启动流程，把 ROM 换成《水晶》：

| # | 操作 | 期望 |
|---|---|---|
| R1 | 内核菜单里设好时间（比如 2026-11-11 14:30） | 菜单显示该时间 |
| R2 | 进《水晶》，游戏内看时钟 | **时分秒接近 14:30**（±1 分钟） |
| R3 | 游戏内看日期 | 2000-03-24 一类（= 9811 mod 512 = 83 天），**不是** 2000-01-01 |
| R4 | 关机等 2 分钟再开，进游戏 | 游戏内时间前进了约 2 分钟，**没有归零** |

R2 是这一版的核心指标。R3 看到"2000 年 3 月"是**正常的**，见 §4。

### 如果 R2 不对

| 现象 | 可能原因 | 怎么查 |
|---|---|---|
| 游戏内还是 00:00 起算 | base 写入没被 FPGA 接受 | 先确认 `$7FC0=6` 时写 `$A018` 有没有效果；上游 RTL 里 `rtc_set_wr` 是否要求 `$7FD0` 之类的前置 |
| 游戏内时间是别的固定值 | `$A01C` 的 halt 位（bit6）没清 → 时钟停走 | 检查写入值 |
| 进游戏后花屏/卡住 | 结束页不是 2，加载命令窗口失效 | 检查 `rtc_base_write()` 的出口 |
| 时间对但日期乱跳 | 天数 9 位截断 + 游戏自己 carry | 预期行为，见 §4 |

## 8. 没做的事

- **不校正走时漂移**。PCF8563 的晶振精度是硬件问题，软件只能每次开机重新对表
  （这一版就是这么做的 —— 每次启动都写 base，所以漂移不会跨会话累积）。
- **不写 `$A008-$A00E`**。那是设置时间的路径（`rtc_write()` + `$7FD0=1` 触发
  PicoBlaze 命令 `$10`），和 base 是两条不同的路。启动游戏时不该动 RTC 芯片本身。
- **不管 MBC5+RUMBLE 之类**。只有 `$0F` / `$10` 带时钟。
