# 许可证与上游关系

这一页回答三个具体问题：**要不要做成 lukesau/ezgb 的 fork**、**有没有用它的代码**、
**AGPL-3.0 要不要换**。结论在每节开头，理由在后面。

---

## 1. 不要做成 fork

**结论：保持独立仓库，不做 fork。**

GitHub 的 fork 不是「参考了某个项目」的意思，它有明确的技术与法律含义：

| fork 意味着 | 本项目实际情况 |
|---|---|
| 与上游共享 git 历史（共同祖先提交） | 我们的第一次提交就是全部代码，和上游没有共同祖先 |
| 页面上永久显示 `forked from lukesau/ezgb` | 会让访客以为这是「改上游的代码」，与事实相反 |
| 适合向上游发 PR（同源补丁） | 我们改的是**另一个产物**：上游在做官方固件的逆向与反汇编（`stage0/`、`re/`），我们写的是一个替代内核 |
| 上游的版权声明与 AGPL 覆盖全部历史 | 我们的代码是独立实现，版权与责任都在本项目 |

fork 还会带来两个实际麻烦：

1. **Issue / PR 混淆**：上游仓库的 issue 列表里会混进「你这个内核备份不了存档」——那
   不是他们的问题；
2. **许可叙事混乱**：fork 会让「是否复制了 AGPL 代码」这个本来很清楚的问题变成需要
   逐行解释的问题。

**正确的关系表达**是：独立仓库 + 在 [NOTICE](NOTICE.md) 与 README 里逐条列出「哪些硬件
事实来自它的文档/反汇编」+ 链接回上游。这也是逆向工程社区常见的做法。

**什么时候才该 fork**：如果我们开始**直接使用上游的 stage1 源码**（比如自己做一个
stage1 或改它的加载逻辑），那就是同一份代码的分支，届时应该 fork 或 vendor 并保留
AGPL 声明。现在没有这一步——我们的产物是被 stage1 加载的 `ezgb.dat`，不与它链接。

---

## 2. 没有直接使用它的代码

**结论：没有复制任何源码、Verilog 或反汇编文本。** 用的是不受版权保护的事实。

| 用到的 | 性质 | 是否受版权保护 |
|---|---|---|
| `$7F00/$7F10/$7F20/$7FF0` 解锁提交序列 | 硬件的操作步骤（事实） | 否（思想/方法/系统） |
| `$A000` 窗口页号 0/2/4/6 的含义 | 硬件语义（事实） | 否 |
| PCF8563 寄存器顺序、`VL` 位 | 芯片数据手册内容（事实） | 否 |
| 元数据页各偏移的用途（`$A000/$A001/$A201/$A300`） | 与官方固件的兼容契约（事实） | 否 |
| FAT16/FAT32 布局、VFAT 长名项格式 | 公开规范（Microsoft FAT specification） | 否 |
| SD 写扇区后空转约 350 次循环 | 实测量（事实） | 否 |

反过来，本项目的**表达**全部是自己写的：

- `crt0.s` / `launch.s` 是自己写的 sm83 汇编（上游 `stage1/src/crt0.s` 是 C 程序的启动，
  目标与段布局都不同）；
- `fat.c` / `fatw.c` / `fatx.c` / `fatn.c` 是手写的 FAT 子集，不是 FatFs，也不是上游的
  `fat.c`（上游那份是 FatFs 的薄封装）；
- `video.c` / `main.c` / `save.c` / `diag.c` 的界面、状态机、元数据记录格式都是本项目
  自己设计的（例如 18 字节带校验、写两份的「上次运行」记录，上游没有这个东西）。

**自查方法**（任何人可以复现）：

```sh
# 1) 上游代码从不出现在构建里
grep -rn "lukesau\|ezgb/" build.sh tools/*.py | grep -v "^Binary"   # 只应出现在注释/文档

# 2) 没有 git 子模块、没有 vendor 目录
git submodule status; ls vendor 2>/dev/null

# 3) 构建只依赖 SDCC + 本仓库 src/
grep -n "sdcc\|sdasgb\|sdldgb" build.sh
```

唯一需要单独说明的是 **FatFs 的算法结构**：v0.13.0 的目录分配是照 `ff.c` 的
`dir_alloc` 思路重写的（`$E5`/`$00` 同等当空槽、不够就扩簇）。FatFs 是 ChaN 的单条款
BSD 风格许可，允许自由使用与再分发；我们没有把它的代码编进 ROM，函数签名、缓冲模型、
错误码都不同，但即便如此也按「参考了」的标准在 [NOTICE](NOTICE.md) 第 4 节写清楚。
这是最保守的做法，不影响本项目的授权选择。

## 3. AGPL-3.0 可以保留，不必换

**结论：法律上不强制 AGPL；建议保留 AGPL-3.0。** 如果目标是「让更多人敢用」，唯一值得
考虑的替代是 **GPL-3.0**（去掉 AGPL 的 §13 网络条款），而不是 MIT。

### 3.1 法律上发生了什么

- 上游是 AGPL-3.0，但**我们没复制它的代码** → 不构成衍生作品 → **不产生 AGPL 义务**；
- 我们链接了 SDCC 的运行时库，而 SDCC 运行时库是 **GPLv2 + Linking Exception**，
  例外条款明确允许与任意许可证的程序链接 → **也不产生 GPL 义务**；
- 界面点阵派生自 SIL OFL 1.1 的字体 → 只约束字体本身（保留声明、不得单卖字体），
  不约束 ROM 的整体许可。

所以许可证是**我们自己选的**，不是被传染的。这一点很重要：它意味着以后想换，法律上
换得动（只要没引入上游代码）。

### 3.2 保留 AGPL 的理由

| 理由 | 说明 |
|---|---|
| 与上游同向，叙事最干净 | 参考了 AGPL 项目的事实，自己也用 AGPL，不会有人质疑「借了 AGPL 的成果却用宽松许可」 |
| 防止闭源硬件商直接拿去卖 | 有人把内核烧进自制卡带卖，必须公开改动——这正是 copyleft 想解决的 |
| §13 对离线固件几乎无成本 | 它只要求「通过网络交互的用户能拿到源码」。一个烧在卡带里的内核没有网络交互，实际义务与 GPL-3.0 相同 |
| 已有发布物都是 AGPL | 现在换等于给历史版本留两套条款，没必要 |

### 3.3 什么情况下值得换

| 场景 | 建议 |
|---|---|
| 想进 Debian/Fedora 等发行版 | 都可以；AGPL 是自由许可证，不是障碍 |
| 想被公司内部工具链采用，而公司法务一刀切禁 AGPL | 换 **GPL-3.0**：条款几乎相同，去掉网络交互那一条 |
| 想做「随便谁都能闭源集成」的生态 | 换 **MIT / Apache-2.0**。代价是别人拿走改闭源你无法阻止；对本项目这种「个人维护的硬件固件」，通常不划算 |
| 以后直接使用上游 stage1 代码 | **不能**换宽松：那时就必须 AGPL-3.0，且要保留上游声明 |

### 3.4 换的话怎么换

1. 只有**版权持有人**能换。如果只有你一个作者，直接改 `LICENSE` + README/NOTICE 的
   表述即可；如果收过别人的 PR，需要征得同意（或保留该部分为 AGPL）。
2. 旧版本已经按 AGPL 发布，**不能追回**：换证只对之后的版本有效，tag 上的旧版本仍是
   AGPL。所以 CHANGELOG 里要写明「从 vX.Y.Z 起改用 XXX」。
3. 别删历史声明。`NOTICE.md` 里对字体（OFL）与上游事实的说明与主许可证无关，换证也要
   保留。

### 3.5 两个容易忽略的点

- **名称与商标**：`EZ-Flash`、`EZ-FLASH Junior` 是 EZ-FLASH 的商标。本项目名字里含
  「EZJR」属于**描述性使用**（说明兼容哪台机器），不能暗示官方认可。README 第一段已经
  写明「不是官方固件」，别在宣传里改掉。
- **不含官方二进制**：官方内核、固件更新包、官方字库都不能进仓库或 Release。`.gitignore`
  已经拦了 `*.dat / *.gb / *.sav`，`EZJR.FNT` 也按生成物不入库。

> 实践上建议保留。**
