## 0. 实施记录（P0，2026-11-11）

计划里的东西全部落地了，但过程中有两处和计划不一样，记在这里：

| 项 | 计划 | 实际 |
|---|---|---|
| 代码增量 | ~1,250 字节 | **1,916 字节**（`_CODE` 从 `$3177` 涨到 `$38F3`），剩余 **781 字节** |
| handoff 实现 | 90 行汇编 | 123 字节机器码，unlock/lock **全展开**（不用 `call`，避免 `$D000` 重定位） |
| 自检屏 | 考虑砍掉腾空间 | **没动**，781 字节够 P1 的 ~300 |

### 测试抓到的两个真 bug（都是主机侧先发现的）

1. **`header_sum` 循环变量溢出**（`src/game.c`）
   写成 `for (i = 0x134; i <= 0x14C; i++)`，`i` 是 `uint8_t` → `0x134` 截断成 `0x34`，
   条件恒真，**死循环**。gcc 的 `-Woverflow` 直接点出来了（"changes value from 308 to 52"）。
   改成相对偏移 `i = 0..0x18`、`h[0x134 + i]`。
   这和 `rtc_weekday` 月偏移表那次是同一类坑：**16 位常量塞进 8 位循环变量的截断**。

2. **`header_sum` 区间写错**（同上）
   传进来的是整扇区（512 字节），header 在缓冲里从 `$100` 起，校验和区间应是
   `$134-$14C` 而不是 `$034-$04C`。寄存器序列测试在第 9 步（`$7FC3`）直接对不上，
   三组用例同时报同一个错，一眼就定位了。

第 2 个 bug 如果不修，后果是**每个游戏都以错误的卡带校验和启动**。上游 `game.c` 是用
`buf[0x100 + i]` 的写法避开这个坑的，我照抄时把 `0x100` 丢了。

### 已完成的验证

| 层 | 结果 |
|---|---|
| 加载命令表 | 8 个用例，512 字节逐字节比对全绿（1/2/3/6/61/62 段、成环、坏链） |
| 寄存器序列 | 3 个用例（MBC3+TIMER / ROM only / MBC5），11 步 golden 序列全绿 |
| handoff 静态 | 123 字节内无 `CALL`/`JP nn`/`JP HL`，所有 `LD HL,nn` 指向 `$7Fxx` 或 `$A000` |
| 模拟器 | 50 项断言全绿（新增 5 项：A 键、错误屏三行、自动回列表） |

### 真机结果（M1，2026-11-11 通过）

`$7F36=3` 之后的装载、`$7FE0=$80` 的复位接管在 PyBoy 里都不存在，只能上卡看。
**真机已通过**：多个 MBC 游戏（ROM-only / MBC1 / MBC3+TIMER / MBC5）都能进入并正常
运行；v0.13.0 又在这一层之上验证了「上次运行」直接启动（不切目录、不重扫列表）。

## 3. 完整启动序列（技术依据）

顺序抄自上游 `stage1/src/game.c: game_launch()` 与 `game_handoff.s`（两者均经真机验证），
细节见 `ezgb/docs/fpga-stage1.md`「Fast launch」与 `launch-trace.md`。**顺序不能改**。

| # | 动作 | 依据 / 陷阱 |
|---|---|---|
| 1 | 读游戏首扇区 `cluster_sector(entry->cluster)`，取 `$0100-$014F` 头 | 只需 1 次 `sd_read` |
| 2 | 由头算 5 个值：`mbc`、`rom_mask`、`ram_mask`、`timer`、`checksum` | 见 §4.2 |
| 3 | 遍历簇链，构建 512 字节命令到 WRAM | 见 §4.1，**最容易错的一步** |
| 4 | **RTC base**：`fpga_page(6)`，写 `$A018-$A01C` | 二进制值，非 BCD；`$A008` bit7(`VL`)=1 则整段跳过 |
| 5 | `fpga_page(2)` | 必须回 2，不能是 0（`win_mode[1]` 约束） |
| 6 | `$7F37 = mbc \| (timer ? 0x80 : 0)` | 一次性写对，**读不回**，写错非 MBC3 游戏直接崩 |
| 7 | FW5 时 `$7FD3=0`、`$7FD4=$11` | 两者**相加**为快加载键；只写 `$7FD4` 在 CGB 上会变 `$22` 反而更慢 |
| 8 | `$7FC4 = ram_mask`；`$7FC1/$7FC2 = rom_mask` 低/高；`$7FC3 = checksum` | 校验和 = `-(sum($0134..$014C)) - 1` |
| 9 | 等 `rLY == 144`，关 LCD（`rLCDC=0`） | 必须在 VBlank 关，否则花屏 |
| 10 | `$7F36 = 1`，512 字节命令 `memcpy` 到 `$A000` | 此时 `$7FC0` 须为 2 |
| 11 | 把 handoff 汇编 `memcpy` 到 `$D000`，跳到 `$D000` 执行 | **第 11 步之后 ROM 就没了** |
| 12 | handoff 内：`$7F36=3` → 轮询 `$A000` 直到 ≥2 → `$7F36=0` → `$7F31=0`、`$7F32=0` → `($2000)=1`、`($3000)=0` → `$7FE0=$80` | 复位进游戏，本内核不再返回 |

> **第 4 步为什么在 `$7F37` 之前**：`clocks.v` 的 `pb_clk_run = kernel_mode | rtc_flag`。
> 先写 `$7F37` 会让 PicoBlaze 立刻按 `base + elapsed` 起算，而 base 还是 0；先写 base
> 则从第一个 tick 起就是对的。这与 1.05e 的顺序一致（`BackupOpenSaverPath` 早于
> `LaunchSetup`）。补丁版是在 `LaunchSetup` 末尾插的，那时的约束不同，不能照搬位置。

## 4. 关键数据结构

### 4.1 load command（512 字节）

| 偏移 | 内容 |
|---|---|
| `+$000` | `0`（一个 32 位 0） |
| `+$004` 起 | 连续段表：每段 `{u32 起始 LBA, u32 累计已加载扇区数}`，**`end` 是累计值不是本段长度** |
| 末段之后 | `$FFFFFFFF`（剩余全部），再接一个 `0` |
| `+$1F0` | 文件字节数 |
| `+$1F4` | `1` |
| `+$1F8` | `csize`（每簇扇区数） |

约束：段数上限 **61**（命令表到 `+$1F0` 为止），超出说明文件碎片过多，必须报错返回，
绝不能溢出（上游注释明确记着溢出会踩掉 `+$1F0` 之后的字段）。

「累计值」的含义：第一段 `end` = 本段扇区数；第二段 `end` = 第一段 + 第二段；以此类推。
前两段时累计值与长度恰好相等，从第三段起才分道扬镳 —— 这是最容易被写错的一处。

### 4.2 ROM 头 → 寄存器值

| 字段 | 头偏移 | 映射 |
|---|---|---|
| `mbc` | `$0147` | `00/08/09`→0；`01-03/EA/FF`→1；`05/06`→2；`0F-13/FC`→3；`19-1E`→4；其余→6 |
| `timer` | `$0147` | `0F`、`10` 为真（这两个就是 MBC3+TIMER） |
| `rom_mask` | `$0148` | `1-8`→`(2<<code)-1`；`$52/$53/$54`→`$47/$4F/$5F`；再按文件实际大小向上取整到 2 的幂 - 1 |
| `ram_mask` | `$0149` | mbc2 或 `code<=2`→0；`4`→`$0F`；`5`→`$07`；其余→`$03` |
| `checksum` | 算 | `x = 0; for i in $0134..$014C: x = x - b - 1` |

## 7. 风险与对策

| # | 风险 | 后果 | 对策 |
|---|---|---|---|
| R1 | handoff 在 WRAM 执行时仍引用了 ROM 里的地址（如调 C 函数、常量表） | 白屏 / 随机死机，且**现象不可预测** | handoff 用纯汇编、只用立即数；`launch.s` 里禁止任何跨段符号引用；反汇编逐条核对 |
| R2 | `$7F37` 写错（MBC 码或 timer 位） | 非 MBC3 游戏崩；或 RTC 游戏不走时 | 由头一次性算出；host test 断言 8 种 cart type 的期望值 |
| R3 | 命令表 `end` 写成段长 | 第三段起内容错位，游戏能进但花屏/崩溃 | 主机测试用 ≥3 段镜像，逐字节比对 |
| R4 | 碎片 > 61 段 | 命令表溢出踩掉 `+$1F0` | 构建前判段数，超限直接报错返回，不启动 |
| R5 | LCD 未在 VBlank 关 | 花屏、`$A000` 写入被撕裂 | 轮询 `rLY==144` 再关 |
| R6 | `$7FC0` 忘记回 2 | `$A000` 窗口不映射，命令写丢 | 代码里 base 写完后立刻 `fpga_page(2)`，host test 断言序列含它 |
| R7 | 32 KB 空间不够 | 链接失败 | 见 §5.3 的三级降级 |
| R8 | 进游戏后无法返回内核 | 只能重启卡 | 这是**设计如此**（上游也一样）；靠 `$7FE0=$80` 复位回引导层 |

> R1 是本轮唯一「模拟器完全测不出、真机出错也难定位」的风险。缓解手段是
> 把 handoff 控制到 90 行以内、只用立即数、写完后用 `sm83dis.py` 反汇编人工逐条核对。

## 8. 验证策略（三层，能测什么就测什么）

| 层 | 手段 | 能覆盖 | 测不到 |
|---|---|---|---|
| 1 算法 | `launch_host_test.py`（gcc + 桩） | 命令表字节、头解析 8 种 MBC、寄存器序列 12 步、碎片/坏链报错 | 硬件行为 |

**PyBoy 测不到启动**这件事要说清楚：`$7F36=3` 在 PyBoy 里只是一次普通内存写，
没有 FPGA 去流式装载 pSRAM，`$7FE0=$80` 也不会复位进游戏。所以第 2 层只能验证
「走到第 11 步之前都是对的」，第 12 步必须真机。这也是为什么要把第 1 层做扎实 ——
它是真机失败时唯一能快速排除的环节。
