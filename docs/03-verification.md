# 验证：四层，各证各的事

原则：**能用机器判定的就不靠"看起来对"**。每层写清「证了什么」「证不了什么」。

| 层 | 工具 | 证什么 | 证不了什么 |
|---|---|---|---|
| 1 静态结构 | `tools/verify_rom.py` | ROM 合法、段不重叠 | 能不能跑 |
| 2 主机侧算法 | `fat_host_test.py` / `rtc_host_test.py` / `launch_host_test.py` / `fpga_host_test.py` / `save_host_test.py` / `window_host_test.py` | FAT 扫描（6 种卷布局）、BCD、星期、加载命令表、启动寄存器序列、handoff 静态检查、`sd_write` 序列、存档写路径（FAT16/FAT32 各一遍，独立解析器核对）、**根目录唯一 `SAVER/` 的创建与小写后缀**、**删除（目录项 + 孤儿 LFN + 簇回收）**、**`fat_locate()` 按目录簇定位 ROM**、**元数据擦除态校验**、**`.SAV` 的 VFAT LFN 目录项**、**$A000 窗口择路模型**（真 fpga/fat/fatw/save.c 全流程） | 编译器/硬件行为 |
| 3 模拟器 | `tools/emu_test.py`（PyBoy） | 真的跑起来、界面/按键/保存、**备份四屏截图** | FPGA 相关（SD/PCF8563） |
| 4 真机 | 人手 | 上面全部 + FPGA：SD 读写、FAT 挂载、PCF8563、启动游戏、中文名 `.sav` | 长周期稳定性（RTC 基准、跨月、坏卡恢复） |

---

## 1. 静态结构（`verify_rom.py`）

- 大小 32768；Nintendo logo 逐字节等于官方 logo；
- `$0143` 头校验和、`$014D` 全局校验和自洽；
- `$0100 = nop`，`$0102 = jp`，目标落在 `_HOME`；
- 段布局升序不重叠（`build.sh` 也会在链接后立刻断言一次）；
- 代码/数据非空、字库数据存在。

**证不了**：程序逻辑、硬件访问是否正确。

## 2. 主机侧算法

### FAT（`fat_host_test.py`）

同一个 FAT16 卷（BPB + FAT + 根目录 8 个条目：2 个 `.GBC`、1 个 `.GB`、1 个 `.TXT`、
1 个已删除、1 个子目录、1 个隐藏、1 个 LFN），分别放进 **6 种真实世界的卷布局**里，
用主机 `gcc` 编译 `src/fat.c` + mock `sd_read` 直接跑：

```
OK   superfloppy 期望 POKEMON.GBC, TETRIS.GB, CRYSTAL.GBC
OK   mbr         期望 POKEMON.GBC, TETRIS.GB, CRYSTAL.GBC   ← MBR 引导代码为 0，分区从 LBA 2048 起
OK   no_label    期望 POKEMON.GBC, TETRIS.GB, CRYSTAL.GBC   ← 引导扇区没有 "FAT" 标签
OK   mbr_gpt     期望 ERR=3
OK   mbr_no_fs   期望 ERR=4
OK   fat12       期望 ERR=2
```

同一个镜像里还带一个 `SUBDIR`（里面有 `.`、`..` 和一个 ROM），每种布局都跑一遍
目录导航：

```
OK   superfloppy 子目录 = 「..」+ 目录内 ROM，返回上级一致
```

即：A 进去只看到 `..` 和 `SUBGAME.GBC`（`.`/`..`/隐藏项不重复列出），
B 退回来列表和进去之前完全一致。

> **这一层在真机之前漏掉了一个致命 bug**：早期判据是「LBA0 的 `0x0B` 处 == 512」，
> 而 MBR 那块是 x86 引导代码，几乎永远不等于 512 —— 所有带分区表的卡都会被判成
> "无签名"。当时只用裸卷（superfloppy）造镜像，所以主机测试全绿、真机 `ERR=01`。
> 真机读数 `SEC0 00 00 00 00 00` + `SIG=55AA OK` 才把它定位出来。
> 教训：**「像真的」不等于「覆盖真实」**，布局必须是穷举的那一维。

> 另有一个真 bug 也在这一层抓到：早期写成 `if (attr & 0x0F) continue`，把**只读**
> （`0x01`）也跳过了——很多 ROM 文件在卡上是只读的，会导致列表漏项。

### RTC（`rtc_host_test.py`）

把 `rtc.c` 内联进测试桩，`WINDOW` 换成普通数组，mock `fpga_set/fpga_page`：

- `bin<->bcd` 0..99 往返；
- `rtc_read`：BCD 解析、高位标志屏蔽、`VL=1` 检出；
- `rtc_write`：页序列必须是 `6 -> 0`，7 个 BCD 写进 `$A008-$A00E`，且最后
  `$7FD0` 先 `1` 后 `0`；
- `rtc_weekday`：**2000-2099 年每月 1/15/28 日共 3600 个日期**，期望值由 Python
  的 `datetime` 生成，全量差分；
- `rtc_base_write`：**20 个时刻**（2000/2004/2008/2020/2024 闰年、平年 2 月、
  2099 边界）的 S/M/H/DL/DH 逐字节比对，期望天数由 `datetime` 算；结束页必须是
  `2`（`tbl_win` 要求 `win_mode[1]=1`）；`VL` 置位时 base 区一个字节都不写、但仍
  切回页 2。变异测试确认有效（删闰年补偿 → 16/20 不符；结尾改 `fpga_page(0)` →
  切页断言失败）。

> 这一层也抓到过真 bug：月偏移表用 `uint8_t` 存 `{0,31,59,...,334}`，
> 273/304/334 被截断成 17/48/78，星期算错。改用 `uint16_t` 后全通过。
> （姊妹项目的 1.04c C 参考实现踩过同一个坑。）

## 3. 模拟器（PyBoy，`emu_test.py`）

PyBoy 是完整的 Game Boy 模拟器，会真的执行 ROM 的机器码。

### 正式版 `build/ezgb.dat`

模拟器里没有 EZ-Flash 的 FPGA，也没有 SD 卡，所以 `fat_mount()` 失败 →
应该停在「存储卡错误」。断言：

- `LCDC` bit7 置位（LCD 开了）、`BGP=0xE4`、`SCX/SCY=0`；
- VRAM 里有约 1000 字节非零（ASCII 字库 + 汉字点阵真的上传了）；
- 第 6 行出现 ≥8 个编号 ≥`$80` 的 tile（汉字），且去重后 ≥5 组（每个字独立分配）；
- 第 9 行显示 `MOUNT FAILED`，第 10 行显示 `ERR=<fat_mount 返回码>`。

**这已经证明**：`crt0` → `video_init` → 字库上传 → 汉字渲染 → 错误分支，整条链是通的。

v0.12.7 改写/新增（都改成**按字节核卡**，不再只看屏幕报什么）：

- **第 12 组：12 个带长名的存档 + 30 字符长名**。真机上那 12 个 `.sav` 是中文名，
  每个占 2 条长名项 + 1 条短名项 = 3 槽，一共 36 槽 —— 这才是真实形状。
  断言顺 FAT 链算出 SAVER 的簇，再断言目录项落点**就在链里**（旧代码在 FAT16
  上会给出 `LBA 65792 / 簇 65535`，一个数据区之外的野扇区）。
- **第 13 组：`$00` 落在扇区尾部**。12 个短名存档占 14 槽，`$00` 停在槽 14
  （扇区尾还剩 2 槽），而长名要 4 槽 → 必须把尾部 2 个 `$00` 标成 `$E5`、
  让追加位落到下一扇区（实测 `Q_ENT` = LBA 266 槽 3）。这条压 v0.12.6 那个
  「腾完位下次就再也写不进」的死结。
- **第 14 组：16 槽填满（连 `$00` 都不剩）**。v0.13.0 起这里断言的是**扩簇**：
  不再返回 `FAT_ERR_ADD_DIR`，而是 SAVER 簇链从 1 簇长到 2 簇、文件项落在新簇
  里（实测 LBA 485 = 簇 228）。这条同时钉两件事：`dir_append()` 真的把簇接上
  了，以及 `dir_nth()` 的链尾判据没退回 FAT32 的 `$0FFFFFF8`（退了就会打印
  「LBA 65792（簇 65535）不在 SAVER 簇链里」）。

  并且中间的 `2.0` 不能被当成扩展名截掉。

> 这一轮在主机侧还抓到三个**只有真机才会发作**的 bug，都写进了断言：
> ① FAT16 的链尾标记 `$FFF8-$FFFF` 小于 `$0FFFFFF8`，`dir_chain()` 只用 FAT32 门限，
> 子目录走到链尾后会把 `cluster_sector(65535)` 当 LBA 读；② 长名项按序号写回缓冲时
> 没判边界，序号大的段会踩坏栈上的循环变量（真机上表现为备份卡死）；
> ③ 扇区循环变量写成 `uint8_t` 又从 0 加到 512，永远出不了循环。

> 自检屏在模拟器里 `SEC0` 是 `FF`、`SIG=BAD`、`FW=--`，属**预期**：
> PyBoy 没有 FPGA，`$A000` 读回 `$FF`。这一屏的断言只验证**渲染与取值路径**，
> 真值必须上真机才能看到。

> 这一层抓到过四个真 bug：
> 1. **列表行与表头重叠**——旧版汉字占 2 行，表头画在行 3 会压掉行 4 的首个游戏名；
> 2. **保存时星期硬写 0**——PCF8563 的 weekday 写 0 是无效值，改为按日期推算；
> 3. **VRAM 写竞态**——`POKEMON` 显示成 `POK.MON` / `PO EMON.GB`。等 HBlank 写也不够
>    （204 周期，读 STAT 到落字要 20 多周期，踩到末尾就整格被吞），改成**只在 VBlank 写**；
> 4. **SDCC 把「写后回读校验」优化掉**——`*v = c; if (*v == c)` 被判定恒真，
>    编译出来只剩一句写，校验根本不执行。所以最后没用回读方案。

### 3.5 启动游戏（`launch_host_test.py`）

启动流程有三层验证，都不需要真机：

**（1）加载命令表 —— 512 字节逐字节比对。** Python 按规范独立算一份期望值，
gcc 编译 `src/fat.c` 拿实际值，逐字节比：

```
OK   single         1 簇，1 段
OK   two_seg        4 簇，2 段
OK   three_seg      6 簇，3 段          <- 从第三段起「累计值 != 段长」
OK   five_single    6 簇，6 段          <- 每段 1 簇，累计值 1,2,3,4,5 vs 段长全 1
OK   max_61seg      61 段（上限）
OK   over_62seg     ERR=5 FRAGMENTED    <- 必须拒绝，不能溢出
OK   loop_as_frag   ERR=5               <- 成环会不断产生新段，先撞段数上限
OK   bad_next       ERR=6 BAD_CHAIN
```

**（2）启动寄存器序列 —— 11 步 golden 断言。** 桩记录每一次 `fpga_set`/`fpga_page`，
与按规范算出的序列逐项比对，覆盖 MBC3+TIMER（水晶）、ROM only（俄罗斯方块）、
MBC5 三种卡带：

```
$7FC0=04, $7FC0=00        <- 读固件版本
$7FC0=02                  <- 命令窗口要求页 2
$7F37=83                  <- MBC3 | timer
$7FD3=00, $7FD4=11        <- FW5 快加载键
$7FC4=0F, $7FC1=3F, $7FC2=00, $7FC3=xx
$7F36=01                  <- 打开命令窗口
LCDC=00                   <- 关屏
```

**（3）handoff 段静态检查。** 这段代码要在 ROM 被覆写后继续执行，所以不能有任何
跨符号引用。检查 `$0400-$047B`（123 字节）：

- 不含 `CALL`（`$CD`）、`JP nn`（`$C3`）、`JP HL`（`$E9`）；
- 所有 `LD HL,nn`（`$21`）的目标都在 `$7F00-$7FFF` 或 `$A000`。

> 这一层抓到两个真 bug，都是**同一类**：`uint8_t` 装不下的常量。
> 一是 `for (i = 0x134; ...)` 被截成 `0x34` 导致死循环；二是校验和区间写成
> `$034-$04C`（少了 `$100` 偏移），导致每个游戏都以错误的卡带校验和启动。
> 第二个 bug 只有「三组不同 MBC 的用例同时在第 9 步报错」这种排布才一眼看得出来 ——
> 如果只测一种卡带，很容易误以为是那个游戏本身的问题。

## 4. 真机（EZ-Flash Junior / FW5 / FAT16 SD 卡）

这一层的每一项都只能实测，模拟器**完全覆盖不到**。当前结论：

| # | 项目 | 结果 | 说明 |
|---|---|---|---|
| 1 | **SD 读扇区** | ✅ | `$7F30/$7FB0` 序列、忙等待 `$A000 == $E1`、512 字节窗口拷贝 |
| 2 | **FAT 挂载** | ✅ | 分区表 + BPB + FAT16；卡上目录与长名都能列出来 |
| 3 | **PCF8563 读** | ✅ | `$7FC0=6` 后 `$A008-$A00E` 是 BCD 时间，`VL` 位有效 |
| 4 | **PCF8563 写** | ✅ | `$A008-$A00E` + `$7FD0=1` → PicoBlaze 经 I2C 写；改完读回等于设定值 |
| 5 | **FW5 版本读** | ✅ | `fw_version()` 读回 5，版本行显示 `MZOS V0.14.0 FW5` |
| 6 | **启动游戏** | ✅ | 加载命令表 → 寄存器 → WRAM handoff → `$7FE0` 复位；多个 MBC 游戏实跑 |
| 7 | **列表 + 中文长名** | ✅ | 文件夹 / `.GB` / `.GBC` 三种短名形状都配上长名；目录在前、按名升序 |
| 8 | **中文名 `.sav` 备份** | ✅ | 12 个中文名存档的目录里新建 32768 字节的 `K 口袋妖怪 水晶 金手指v3+全道具251+NPC加强版2.0.sav` |
| 9 | **上次运行的游戏** | ✅ | `$A300` 记录跨断电有效；START 菜单直接启动，不重扫列表 |
| 10 | **删除 ROM** | ⚠️ 主机侧 | 目录项 + 孤儿 LFN + 簇回收都有断言，真机未逐项确认 |
| 11 | **游戏内 RTC 基准** | ⚠️ 待验 | 页 6 `$A018-$A01C` 写入序列已实现，未在 MBC3 游戏上做长周期对照 |
| 12 | **无卡 / 坏卡** | ⚠️ 部分 | `sd_read` 忙等有 65536 次超时保护；「拔卡后插卡」的恢复未系统测 |
| 13 | **目录塞满后的扩簇** | ⚠️ 待验 | 主机侧已验证（16 槽填满 → 链长 1→2 簇），真机未压到那个边界 |

> 第 8 项是 v0.13.0 的关键一步。它前面失败过七版，根因不在「名字」而在目录层：
> 空槽只数一个扇区、把 `$00` 改写成 `$E5` 挪追加位、FAT16 链尾判据用成 FAT32 的。
> 换成 FatFs 的 `dir_alloc` 写法（`$E5`/`$00` 同等当空槽、不够就扩簇）之后一次通过。
> 完整推理链见 [CHANGELOG](../CHANGELOG.md) 的 v0.12.2–v0.13.0。

**仍然证不了的**：跨月/跨年的 RTC 漂移、反复插拔的耐久、坏块卡的降级行为。这些只能靠
长期使用反馈，不在自动化范围内。
